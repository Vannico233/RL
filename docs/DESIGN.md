# 实现与证据说明

## 一条轨迹如何进入训练

1. 准备程序读取官方划分，检查图像 ID、文件和 RGB 像素哈希，冻结题池。`solution` 保存在训练元数据中，不进入模型消息。
2. 首张观察图按 28 像素网格和面积预算生成。提示明确使用这张图的像素坐标；工具保留原图，以宽高比例映射请求框，左上取 floor、右下取 ceil。
3. 模型生成裁剪动作。调度器验证请求，从原图裁剪并把真实 PIL 图像追加到交互历史。每次有效或非法动作均消耗一次预算，最多两次，第三轮用于最终回答。
4. ms-swift 保存模型实际采样的 token IDs、log-probabilities 和逐轮 loss mask。项目不重新分词或改写采样结果，也不把环境返回当成模型生成内容。
5. `rollout_infos.images` 将动态图片同步回训练样本。框架用实际采样 IDs 重建 assistant 内容，user 工具回传及图像占位符参与条件输入但不作为预测目标。
6. 评分器只读取最终 `<answer>`，用固定 ChartQA 协议产生 0/1 奖励。GRPO 的组内优势、策略损失、反向传播和 vLLM 权重同步由固定版本 ms-swift 完成。
7. 运行审计记录可训练参数、梯度、参数变化、同步完成回执，以及更新后的注册 adapter 生成；这些证据共同用于 G1。

系统提示、数据导出、训练和独立评估共享协议与裁剪实现。评估使用 Transformers 贪心解码，训练使用 vLLM 采样；最终成绩统一来自前者。

## 图像与调用预算

| 条件 | 最大像素面积 | 说明 |
| --- | ---: | --- |
| 普通整图 | 1,003,520 | 约 1,280 个合并后的视觉 token 上限 |
| 高分辨率整图 | 2,007,040 | O1 对照 |
| 每张裁剪图 | 501,760 | 从原图取像素，再按预算处理 |

尺寸必须是 28 的倍数。预算是上限，不能假定每张图片实际恰好达到上限。两次调用不会递归裁剪第一次局部图。越界、非有限数值、反向框、过小区域等均返回明确错误，不静默修改成另一动作。

O2 固定区域为原图长轴的两半；O3 的面积与宽高比范围固定，并使用题目 ID 加种子生成确定性随机框。O2/O3 在问题中明确说明额外观察是预先提供的，不伪造模型曾请求这些区域。D0 只接收验证集的人工诊断框。

## 公平比较

- B0/B1/B2 使用同一基座或同一合并后的 SFT 初始化；B1/B2 使用相同题池、奖励和基础训练预算。
- O0–O4 使用固定 checkpoint 与同一题集。改变观察方式会引起分布变化，属于机制诊断，不能自动等同严格因果识别。
- 按所有评估题汇总，包括错误和解析失败；缺失成本保留为空并报告覆盖率。
- 同图多问的置信区间采用按图表聚类的配对 bootstrap。它不提供跨训练种子的结论。
- 训练步数相同不等于成本相同。训练汇总按 request ID 去掉重复编码，并分开记录训练和周期验证，报告实际样本覆盖与生成/视觉 token。

## 复用与新增范围

复用：Qwen2.5-VL 模型与处理器，ChartQA 数据，ms-swift 的 GRPO/多轮基础调度/LoRA/权重同步，以及 Pix2Struct 的评分约定。

本仓库实现：严格工具与答案协议、原图坐标映射和预算管理、数据清单与去重、规则奖励、ms-swift 插件接入、运行证据检查、B0/B1/B2 与 O0–O4 评估、可选核查式 SFT、成本记录及案例展示。

本仓库未重写 GRPO，也没有预先证明新算法或准确率提升。作为个人项目使用时，应能独立解释、修改并在服务器验证以上链路，再据实际工作和结果陈述贡献。

## 可检查但仍有限的证据

- 静态源码检查确认固定版本中的接口存在，不能代替真实集成测试。
- G1 的编码检查验证损失 token 与采样 IDs、图像网格和 log-prob 数量一致，不直接逐元素验证模型内部所有多模态位置张量。
- 同步回执加更新后 adapter 注册记录不能等同生成端 tensor 逐字节校验。必要时用同一输入检查更新前后输出分布，并结合框架日志排错。
- 保存的显存峰值属于训练进程；单独的 vLLM 进程显存需要结合服务器监控记录。
- 代码、模型、数据和实际环境留有哈希或版本记录；随机硬件算子仍可能影响完全逐位复现。
